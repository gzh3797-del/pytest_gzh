# 生成后覆盖门禁（COVERAGE_GATE）

> 借鉴测试二组 `quality-gate validate`（Gate2/3 零漏项）+ `autotest` 探查约束表可追溯性（铁律 2）。
> 本门禁是 **AI 自检**，不依赖外部 Workflow/CLI。它拦截 pytest **跑得过但没真正断言**、
> **凭空捏造选择器**、以及 **改了配置不还原（污染后续用例）** 三类静态检查发现不了、运行也未必暴露的问题。

门禁在**生成脚本后、跑 pytest 前**执行（对每个 `test_*.py` 独立）。跑 pytest 只验运行期问题；
本门禁验"覆盖 + 可追溯"，两者互补，缺一不可。

---

## 一、探查约束表（Constraint Table）——codegen 前必产出

**在为一个用例写任何代码之前**，先把该用例要用到的每个控件/字段/断言值整理成一张表，
每行注明**证据来源**（命中的 `*_context.md` 某节，或本次 playwright-mcp 探查记录）。
约束表是代码的**唯一事实源**。

```
探查约束表 — <用例编号>
──────────────────────────────────────────────────────────────
控件 / 字段 / 断言目标   探查证据（来源）                          代码写法
──────────────────────────────────────────────────────────────
Save 按钮               context: Devices_..._context.md §3        get_by_role("button", name="Save")
Device Name 输入        探查 innerText="Device Name"（无冒号）     get_by_label("Device Name", exact=True)
名称>40 报错            context §实测: .el-form-item__error 文案   expect(err).to_be_visible()
列表"Official"列显示值  探查实测列文本="Yes"                       assert cell == "Yes"（非表单选项"Official"）
──────────────────────────────────────────────────────────────
```

**硬规则：**
- 约束表**留白（未探查）的项，禁止凭推断写代码** —— 必须先补探（走 `analyze-web-page`）或将该用例转红记根因。
- 断言的**列显示值/数值**必须来自实测证据，不得用"表单选项文本"或"看起来合理的数字"替代。

---

## 二、门禁项（每个 `test_*.py` 逐条自检）

### Gate A — 可追溯性（对应"严禁编造"，硬门禁）
逐个检查生成代码里出现的**每一个** locator 字符串、label/placeholder 文本、断言期望值：
- 能在该用例的约束表找到对应行 → 通过。
- 找不到（无论"看起来合理的猜测"还是"套用别的模块惯例"）→ **Gate A 失败**：回补探查更新约束表，或将用例转红记根因，**不放行**。

### Gate B — 步骤覆盖（零漏项）
把用例 `测试步骤` 按行拆成步骤清单，逐条判定代码是否实现：

| 判定 | 含义 | 计分 |
|------|------|------|
| implemented | 代码有语义对应的操作 | 1 |
| partial | 有操作但不完整（缺等待/缺参数/顺序错） | 0.5 |
| **missing** | 步骤在代码中找不到对应操作 | 0 → **零漏项失败** |

`gate_b_score = (implemented + 0.5*partial) / 总步骤数 * 100`

### Gate C — 预期覆盖（零漏项）
把用例 `预期结果` 按行拆成预期清单，逐条判定代码是否有对应断言：

| 判定 | 含义 | 计分 |
|------|------|------|
| implemented | 有 `expect/assert` 语义匹配且条件充分 | 1 |
| partial | 有断言但偏弱（只判存在、不判内容/文本/状态） | 0.5 |
| **missing** | 预期结果在代码中无对应断言 | 0 → **零漏项失败** |

`gate_c_score = (implemented + 0.5*partial) / 总预期数 * 100`

**反模式（判为 partial，需拆强）：**
- `assert A or B or C` —— 多个并列预期要拆成各自独立的 `assert`。
- "仅显示/只列出/只保留" 类预期 —— 必须遍历所有可见行（前 N 行）逐行断言，只验第一行 = partial。
- 断言写在 `_helper` 内部但 test 函数体无显式 assert —— helper 内断言**不计分**（视作黑盒）。
- `pytest.skip()`（环境/数据缺失导致的条件跳过）—— 计 implemented，不扣分。

### Gate D — 配置恢复（对应"测试过程配置恢复"，硬门禁）
先判定该用例是否修改了被测设备/系统配置（开关、模式、阈值、通信参数、权限、时间/日期等）：

| 判定 | 含义 | 结论 |
|------|------|------|
| N/A | 纯只读用例，无配置副作用 | 通过（不适用，不扣分） |
| restored | 每个被改配置项都在 `finally` 中无条件还原为测试前原值 | 通过 |
| **partial/missing** | 有配置副作用但：无 `finally` 恢复 / 恢复只写在正常路径（失败即泄漏）/ 只还原了部分被改项 / 用臆造默认值当原值 | **Gate D 失败** |

**硬规则：**
- 有配置副作用的用例，**必须**存在与所有被改项一一对应的还原动作，且位于 `finally`（无条件执行）。
- 还原基准是**实际读取的原始值**，不是猜测的默认值；还原目标值须能回溯到约束表或 context。
- 数据清理（删用户/删数据/登出）**不能替代**配置恢复；两者都缺项都算未过。

### Gate E — 步骤↔脚本语义对照矩阵（零语义偏差，硬门禁）

Gate B/C 只查"**有没有**对应代码"（存在性）；Gate E 进一步查"代码是否**忠实反映**步骤/预期里的**关键参数**"（语义符合度）。存在性通过、但参数写错的情况（如角色 `view` 写成 `edit`、填错"谁的"密码、断言值/文案不对、操作目标对象错）靠 B/C 抓不到，必须由 Gate E 拦截。

做法：把每条 `测试步骤`/`预期结果` 抽出**关键参数**，逐条与代码成对比较，产出一张**边框对照表**。该表同时承载 B/C 的 L1 覆盖列与 E 的 L2 语义列，是**回显与报告的统一产物**（见 SKILL.md Step 7）。用带边框的表格样式（`┌┬┐├┼┤└┴┘`）便于逐行对照：

```
对照矩阵 — <用例编号>
┌──────────────────────────┬──────────────────────────────────────┬───────┬──────────────────────────┐
│ 步骤/预期(原文精简)       │ 脚本对应(函数:行 / 断言)               │ L1/L2 │ 成对比较值(用例值↔脚本值)│
├──────────────────────────┼──────────────────────────────────────┼───────┼──────────────────────────┤
│ user2 权限=edit           │ _PERM_MAP User=edit:L43                │ ✅/✅ │ edit ↔ edit              │
│ user3 权限=view           │ _create_user(role=view):L173           │ ✅/✅ │ view ↔ view              │
│ 填当前用户(user2)密码     │ verify.fill(_INIT_PWD2):L217           │ ✅/✅ │ 操作者自身 ↔ _INIT_PWD2  │
│ 修改成功                  │ toast "password changed":L245          │ ✅/✅ │ 成功文案 ↔ password chg  │
└──────────────────────────┴──────────────────────────────────────┴───────┴──────────────────────────┘
```

- **列**：`步骤/预期` | `脚本对应`（回显用 `函数名:行号`；写进用例文件头的模板改用**代码锚点**，比行号稳、不随改动漂移）| `L1/L2`（覆盖/语义，各 ✅/❌）| `成对比较值`（`用例值 ↔ 脚本值`，L2 的判据）。
- **完整落地样例**见 `projects/AcuHMI_1_7/tests/ui/usermanagement/passwordchange/test_TestCase_ARM_XXL_002_04_case1_06.py` 文件头，可照抄。

**关键参数抽取范围**：身份 / 角色 / 权限级别、输入值、操作**目标对象**、断言的**具体值/文案**、（有副作用时）改了什么 / 恢复到什么。步骤为自然语言时先抽成结构化清单再比对（复用 §一约束表）。

**硬规则：**
- L2 判定**必须写出成对比较值**（`用例值 ↔ 脚本值`）；只打 ✅ 不给比较值 = 视作未做 → 判 partial。
- "脚本对应"列必须给**真实 `函数名:行号` / 具体断言**（与 Gate A 一致），不得虚指。
- 任一行 **L2 = ❌**（关键参数不符）→ **Gate E 失败**，按零漏项处理（修或转红），不放行。
- 纯 UI 呈现类步骤无参数可比 → L2 记 `—`（不扣分）。

## 三、判定与放行

```
verdict:
  Gate A 失败                                   → FAIL（编造嫌疑，转红/补探，不放行）
  Gate D 失败（有配置副作用但恢复缺失/不完整）  → FAIL（无视加权分，补齐 finally 恢复后重评）
  Gate E 失败（对照矩阵有 L2=❌，关键参数不符） → FAIL（无视加权分，改对参数后重评）
  Gate B 或 Gate C 有 missing（零漏项未过）     → FAIL（无视加权分）
  加权分 = Gate B*50% + Gate C*50%
    ≥95                                         → PASS
    70~94                                       → PASS_WITH_WARNINGS（做一次二次自评复核，结论分歧>5% 记"需人工复查"）
    <95 但无 missing                            → 修补后重评
    <70                                         → FAIL
```

- **仅** verdict ∈ {PASS, PASS_WITH_WARNINGS} 的用例才进入 Step 5 跑 pytest 并有资格标 `是`。
- verdict = FAIL：
  - 缺步骤/弱断言/缺配置恢复/语义不符 → 按清单**补齐或改对后重评**（最多 3 轮，与调试循环共享轮次预算）；
    Gate D 缺项直接补 `finally` 恢复动作，Gate E 缺项直接把参数改对，均不涉及转红。
  - 3 轮仍无法覆盖（如预期结果本身模糊无法断言）→ 将该用例**转红**并在「需补充信息」列记根因，
    调试结果列写 `调试失败|门禁未过:缺<步骤/预期/配置恢复/语义不符>`，绝不为放行而删步骤或凑弱断言。

## 四、汇报接入（Step 7）
每条用例除完整 `用例编号` + 测试逻辑外，附门禁结论：
```
TestCase_AcuHMI_009_08_case01  覆盖门禁 PASS（B100/C100，D:restored，E:符合）  测试逻辑：名>40 保存失败、<=40 保存成功
TestCase_AcuHMI_xxx            覆盖门禁 FAIL（C 缺"列表刷新后仍存在"预期）→ 已转红待澄清
TestCase_AcuHMI_yyy            覆盖门禁 FAIL（D 缺"改后未在 finally 还原通信参数"）→ 补 finally 恢复后重评
TestCase_ARM-XXL_002_04_case1_06  覆盖门禁 FAIL（E: user3 角色 用例=view↔脚本=edit）→ 改对参数后重评
```
- **回显中必须打印每条用例的「对照矩阵」（Gate E 表）**，便于测试人员逐条核对步骤↔脚本、快速定位语义偏差。矩阵格式见 §二 Gate E。失败用例尤其要展开矩阵、高亮 ❌ 行。
